# 工具调用兜底 · 第三部分：LLM 修复错误工具调用格式

> 状态：草案（未实现）—— 2026-08-22
> 范围：工具调用兜底的**第三部分（LLM 修复）**。第一部分（意图识别，`tool-call-fallback-design-phase1.md`）回答「模型想不想调工具」；第二部分（CDATA slot，`tool-call-fallback-cdata-slots.md`）把超长 CDATA 内容替换为占位符、让修复层只处理骨架；本部分实现**用 LLM 把格式错误的工具调用代码修复成正确格式**。
> 前置：理解 phase1 的 `SawToolCallIntent` / `original` / `residual` 坐标系约定，以及 cdata-slots 的 `DS_SLOT_{idx}` 占位符机制与 §4 降级语义。

---

## 0. 背景与目标

第一部分已能可靠识别「模型想调工具但格式坏了」的意图（`SawToolCallIntent=true`）。但当格式错得超出**确定性规则**能修的范围——本地名写错、结构严重损坏、闭合标签错位、wrapper 混乱——第二部分 slot 机制只负责「保护 CDATA 内容不被误改」，并不解决「把结构修对」本身。

本部分引入 **LLM 修复器**：把第一部分识别出的、解析失败的坏工具调用代码，交给一个 LLM，让它严格按「工具调用格式规范」修复成正确格式。LLM 是兜底的**最后一环**，前两环（意图识别、CDATA slot）都已就位，本环节处理「意图为真、但规则修不动」的残余坏码。

核心结论一句话：

> 触发条件是第一部分意图为真且确定性修复无法处理；修复动作是「格式规范 + 固定提示词 + 坏工具调用代码」三合一发给 LLM（**同一账号 · vision 模式 · 关闭思考 · 新建对话**）；对 LLM 输出按「正确格式 / `NO TOOL` / 无法解析或超时」三路分支处理——①正确格式则替换为工具调用，②`NO TOOL` 则原样输出兜底片段，③无法解析或超时则原样输出兜底片段。

---

## 1. 修复对象与输入

**修复对象** = 第一部分识别出的**坏工具调用代码片段**（即 `original`/`residual` 中解析失败、但 `SawToolCallIntent=true` 的那段文本）。

**输入三要素**（按序拼接，构成发给 LLM 的完整 prompt）：

1. **工具调用格式规范（tool_prompt）** —— 即系统提示中那段「工具调用格式规范 — 请严格遵照执行：`<|EPSE|tool_calls>…`」的完整说明（含规则 1–15 与「请记住：使用工具的唯一正确方式是在回复末尾使用 `<|EPSE|tool_calls>…</|EPSE|tool_calls>` 代码块」）。必须**完整提取**、逐字保留、不作删减或改写。
2. **固定提示词** —— 固定文本，逐字如下：
   > 请根据上述说明的工具调用说明，修复以下错误的调用代码。直接输出修复后的格式，无需解释哪里错了，也无需说任何话。注意，工具调用的实际参数已用变量代替。直接原样输出即可。
   >
   > **实现修订**：原设计末尾还有一句「如果你认为接下来的内容只是在正常聊天，直接返回 NO TOOL」。实测这句容易误导模型把坏格式工具调用判成普通聊天而直接返回 `NO TOOL`，导致该修的调用不修，因此**暂时移除**。②分支（`NO TOOL`）的判定代码保留不变，模型自发返回时仍按非工具调用处理。
3. **坏工具调用代码** —— 第一部分提取的、格式错误的那段工具调用（交给 LLM 修复的目标）。

---

## 2. 修复流程（时序）

```
SawToolCallIntent=true 且 确定性修复（第二部分 + 规则修复）无法处理
  → [提取] 取 tool_prompt 工具调用格式规范（完整、不删减）
  → [拼接] LLM prompt = 格式规范 + 固定提示词 + 坏工具调用代码
  → [调用] 发 LLM（同一账号 · vision 模式 · 关闭思考 · 新建对话；超时 10 秒）
  → [分支] 按 LLM 输出走三路：
      ① 返回正确工具调用格式 → 解析为工具调用 → 替换到输出中
      ② 返回字面量 NO TOOL    → 该片段并非工具调用 → 兜底片段原样输出，不做任何更改
      ③ 无法解析 / 10秒超时   → 兜底片段原样输出
```

---

## 3. LLM 调用配置（硬约束）

| 配置项 | 值 |
|---|---|
| 账号 | 与本次修复请求**同一账号** |
| 模式 | **vision 模式**（`deepseek-v4-vision` → `model_type=vision`）<br>*实现修订：原设计为专家模式，现改用 vision 模式，把专家额度留给主请求* |
| 思考 | **关闭**（不启用 thinking / reason） |
| 会话 | **新建对话**（不沿用任何旧上下文，避免污染） |
| 超时 | **10 秒**——超时即走③分支（兜底原样输出） |
| 输出 | 只接受纯工具调用格式（`<|EPSE|tool_calls>…`）；不接受解释文字；模型自行返回字面量 `NO TOOL` 时按②分支处理（提示词已不再主动要求返回 `NO TOOL`） |

---

## 4. 三路分支详细语义

| 分支 | LLM 输出 | 处理 | 兜底结果 |
|---|---|---|---|
| ① 正确格式 | 能解析为 `(<|EPSE|tool_calls>…)` 工具调用 | 解析成工具调用，**替换到输出中**（进入正常工具执行链路） | 坏码被修复，输出为正确工具调用 |
| ② `NO TOOL` | 字面量 `NO TOOL` | 该片段并非工具调用 | 兜底片段**原样输出**，不做任何更改 |
| ③ 无法解析/超时 | 非工具调用格式、或 10 秒未响应 | 无法确认 | 兜底片段**原样输出** |

---

## 5. 与第一、二部分衔接（硬约束）

1. **触发位置：finalize 兜底（非流式路径 + 流式定稿）。** 逐 chunk 的流式 sieve 仍必须同步/确定性修复（phase1 §5.3），不允许在增量阶段依赖异步 LLM 调用，否则卡住实时流。但 LLM 修复现已接入**所有流式 finalize 定稿路径**（chat / responses / claude / gemini）：当流已把坏文本 delta 发给客户端、但**尚未发出结构化 tool_calls、也未最终定稿**时，`BuildTurnFromStreamSnapshot` 在交付最终帧之前触发一次 LLM 修复。
   - **发送前替换语义（M4，已定案）**：一旦修复成功得到 `tool_calls`，最终交付给客户端的响应**以修复后的结构化 tool_calls 为准**——有 tool_calls 即无 visible text（phase1 §5.3 渲染语义），坏文本不再作为可见正文暴露。各协议 finalize 在拿到修复后的 `turn.ToolCalls` 时发出 tool_calls 帧、并丢弃缓冲的坏正文。
   - **不可撤回已发 delta 的退化**：若坏文本已作为 delta 流出且无法撤回，至少保证最终定稿产出的 `tool_calls` 正确、错误残留文本在最终 content 层被替换/剥除，让客户端拿到修复后的调用而非坏码。
   - **已发 tool_calls 不再修复**：若结构化 tool_calls 已在增量阶段流式发出（`AlreadyEmittedCalls` / `AlreadyEmittedToolRaw`），finalize **不再**触发 LLM 修复（已发结构无法撤回）。
2. **部分成功也修复并合并（M3，phase1 §5.1 已定案）：** 触发条件是 `SawToolCallIntent` 为真且残余 `ResidualIntentText` 非空——**即使已经解析出 ≥1 个成功 call**，只要仍有坏残片就对残片走 LLM 修复，并把修复出的 call **合并进已有成功 calls**（已有 calls 在前、修复残片在后，按 name+input 去重）。合并后统一走 `NormalizeParsedToolCallsForSchemas`，不破坏已有成功 calls 的解析与归一化。
3. **单次输出只修复一次（H1）：** 非流式重试路径的**中间态收集**（`collectAttempt`）**不得**携带 repair invoker；仅终态 build 携带，确保同一次上游输出只发起一次 `deepseek-v4-vision` 修复 completion、只创建一个 repair session。
4. **CDATA 保护：** 交给 LLM 前，CDATA 内容已由第二部分 slot 成 `DS_SLOT_{idx}` 占位符，LLM 只处理「骨架 + 短占位符」，不接触真实长内容（避免 token 爆炸与内容被误改）。
5. **占位符保留：** LLM 输出中的 `DS_SLOT_{idx}` 必须**原样保留**、不得改写；修复完成后由 `restoreCDATASlots` 按占位符逐字节还原。
6. **会话回收（M2）：** repair invoker 每次 `CreateSession` 新建的 throwaway 会话，在修复完成后（无论成功 / 失败 / 超时）**一律删除**，接入项目已有的会话删除机制（同 `autoDeleteRemoteSession` 的做法）。删除动作跑在与请求/修复 10s 超时**分离**的 context 上（`context.WithoutCancel` + 独立超时），既不被修复超时错误取消，也不拖长主请求；删除失败只记日志、不影响修复结果。
7. **降级安全：** 任何一步失败（提取失败、LLM 报错、解析失败、超时）都不得让坏码以「看似成功」的形式进入下游——一律走兜底原样输出，绝不让占位符字面量（`DS_SLOT_0`）或半修复内容传给下游。

---

## 6. 边界条件

- **LLM 输出带解释文字**（如 "Here is the fixed code:" 前缀）→ 视为无法解析 → ③分支兜底。可选优化：尝试提取输出中首个 `<|EPSE|tool_calls>` 代码块，提取失败才走③。
- **LLM 输出多段/多个工具调用** → 默认只取一个工具调用块（一次修复一个 wrapper/invoke），多块按序逐个处理；无法判定时走③。
- **LLM 改动占位符 `DS_SLOT_{idx}`** → `restoreCDATASlots` 还原时字节比对失败 → 整体降级到「不 slot 的原始兜底路径」（cdata-slots §4），绝不出错渲染。
- **网络/上游错误、超时** → ③分支兜底，原样输出。
- **坏码实际是合法内容（LLM 判 `NO TOOL`）** → ②分支，原样输出，不误触发修复。

---

## 7. 已定决策项

1. 触发 = 第一部分意图为真 + 确定性修复（第二部分 + 规则修复）无法处理。
2. LLM 修复在 finalize 路径触发：非流式 finalize，以及**流式定稿（发送最终帧之前）**（M4）。逐 chunk 增量阶段不引入异步 LLM。
3. 三路分支（①正确格式 / ②`NO TOOL` / ③无法解析或超时）语义如上，任何分支都不让占位符字面量或半修复内容进入下游。
4. **部分成功也修复并合并（M3）**：`SawToolCallIntent && ResidualIntentText != ""` 时即使已有成功 calls 也修复残片，修复出的 call 合并进已有 calls（去重、已有在前）。
5. **单次输出只修复一次（H1）**：非流式中间态收集不带 repair invoker，仅终态 build 触发一次修复。
6. **repair session 必删（M2）**：修复会话在完成后一律删除，接入会话删除策略，删除跑在分离的 context 上。

## 8. 覆盖矩阵（LLM 修复 vs 场景）

| 场景 | 预期行为 |
|---|---|
| 坏码能被 LLM 修复成正确格式 | ① 解析为工具调用，替换到输出 |
| 坏码其实不是工具调用（LLM 判 `NO TOOL`） | ② 兜底片段原样输出 |
| LLM 修复失败 / 超时 / 输出不可解析 | ③ 兜底片段原样输出 |
| 坏码含超长 CDATA | slot 成 `DS_SLOT_{idx}` 占位符交给 LLM，还原后字节一致 |
| LLM 改写占位符 `DS_SLOT_{idx}` | 字节比对失败 → 降级到不 slot 的原始兜底路径 |
| LLM 输出带解释文字前缀 | 无法解析 → ③ 兜底原样输出（可选尝试提取代码块） |
| 流式增量阶段遇到坏码 | 不触发 LLM 修复（需同步/确定性），交流式 finalize 定稿处理 |
| 流式 finalize 定稿：坏文本已 delta、未发 tool_calls | 发送最终帧前触发 LLM 修复；成功则以修复后 tool_calls 交付，坏文本不作为可见正文（M4） |
| 流式已发出结构化 tool_calls | 不再触发 finalize 修复（无法撤回已发结构） |
| 部分成功：成功 call + 尾随坏残片 | 成功 call 保留，坏残片走 LLM 修复并合并进已有 calls（M3） |
| repair session | 修复完成后（成功/失败/超时）一律删除，不泄漏（M2） |
| 非流式中间态收集 | 不带 repair invoker，只在终态 build 触发一次修复（H1） |
